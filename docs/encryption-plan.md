# Plan: encryption (KMS, ACM, manual encryption)

Status: planned. `src/app/api/kms/kms.md` only lists KMS operations and says "we don't encrypt anything, just register the keys, but we validate access". This plan keeps that as the default and adds what is needed on top. Nothing here is implemented.

## Goals

1. **KMS keys and their access rules** emulated well enough to predict who can use a key, and to explain why a call fails: key policy, IAM policy, grants, key state, conditions (`kms:ViaService`, `kms:CallerAccount`, `kms:EncryptionContext:*`, `kms:GrantIsForAWSResource`), cross-account use.
2. **Fake encryption where possible**: services that "encrypt with a KMS key" record the key and enforce the key's access rules and state, without encrypting their data (an S3 object stays a plain file; the metadata says `aws:kms` and the key).
3. **Manual encryption**: the KMS crypto operations (`Encrypt`, `Decrypt`, `GenerateDataKey`, `ReEncrypt`, `Sign`, `Verify`, ...) really work, so client-side code, the AWS Encryption SDK, the S3 encryption client and a developer typing `aws kms encrypt` get real, decryptable results from the simulator.
4. **ACM with real X.509 certificates**, so TLS can really be terminated by emulated endpoints and certificate problems are observable.
5. **Track KMS key policy conflicts**: find, explain and report the situations where a key policy, IAM policies, grants, SCPs and service integrations disagree.

## KMS

### Key state and the API

Keys, aliases, key policies, grants, rotation, key states (`Enabled`, `Disabled`, `PendingDeletion`, `PendingImport`, `Unavailable`), deletion windows (7 to 30 days) with `CancelKeyDeletion`, multi-Region keys later. The operation list is in `kms.md`. Key records live in `db/<account>/<region>/kms.json`; **key material is generated by the simulator and stored with the key** (it never comes from a real account, see the snapshot plan). Quotas (keys per Region, aliases per key, grants per key, request rates) go through the [quota registry](./quotas-plan.md). Lifetime rules: a key cannot be deleted at once, a pending deletion key refuses use, deleting an alias does not delete the key, a disabled key makes every dependent service operation fail with the service's real error.

### What crypto is real

Recommended, because the semantic checks (wrong key, wrong context, tampered blob, disabled key) then follow from the crypto instead of being re-implemented:
- **Symmetric keys** (`SYMMETRIC_DEFAULT`): AES-256-GCM with the key material the simulator holds; the encryption context is the additional authenticated data, the ciphertext blob is self-describing (key ID, key version, context hash, nonce, ciphertext, tag), so `Decrypt` without `KeyId` works as in AWS and a wrong context fails with `InvalidCiphertextException`. 4096 byte plaintext limit as in AWS; `GenerateDataKey*` returns a real random key and its encrypted copy.
- **Asymmetric keys** (RSA, ECC) and **HMAC keys**: real keys generated with Node's crypto, `GetPublicKey` returns the real public key (DER), `Sign`/`Verify`/`Encrypt`/`Decrypt` and `GenerateMac`/`VerifyMac` use them, so a signature made by the simulator verifies with standard tools.
- Ciphertexts are **not** compatible with real AWS KMS (the format is the simulator's); say so in the docs. Key import (`GetParametersForImport`, `ImportKeyMaterial`) and external key stores are later.

### Services: fake encryption

Services call KMS the way AWS does: as a **service acting for the caller**, through the same registry path as any client (decode, authorize, handler), with the caller's identity and the context keys for service use (`kms:ViaService` such as `s3.eu-west-1.amazonaws.com`, `aws:CalledVia`, the grant created by the service for itself). Examples:
- S3 `PutObject` with SSE-KMS needs `kms:GenerateDataKey` (and `kms:Decrypt` for multipart) for the caller on the key; `GetObject` needs `kms:Decrypt`; a disabled key gives `KMS.DisabledException` from S3. The object data on disk stays plain; the metadata records the key.
- SSM `SecureString` parameters (`WithDecryption`), Secrets Manager, Lambda environment variables, EBS, RDS, CloudWatch Logs, SQS/SNS: record the key and check access on read and write.
- An optional **real at-rest mode** (off by default): the service stores data encrypted with a data key from `GenerateDataKey`, so the stored files cannot be read without the simulator. Useful to test code that reads the store directly; costs complexity, so it comes last and is only for S3 first.
- Grants: services that need long-lived access create grants (`CreateGrant` with `GrantIsForAWSResource`); grants are listed, retired and revoked, and are part of the evaluation.

### Manual encryption

Everything in "what crypto is real" is exposed through the normal KMS API from the start of the crypto work, independent of the service integrations: `aws kms encrypt`, SDK calls and client-side encryption libraries work against the simulator, and the results are decryptable by the same account's callers that the key policy allows. This is also the way to test key policies without any other service: encrypt as one principal, decrypt as another.

### Access evaluation and key policy conflicts

KMS differs from most services: the **key policy is the primary access control**, and an IAM policy only counts if the key policy lets it (the `Enable IAM policies` statement for the account root, or a direct allow). The evaluation, which belongs to the policy engine ([architecture.md](./architecture.md)) with a KMS-specific layer, is: SCP and RCP, permission boundary and session policy, then key policy (explicit deny, allow for the principal or for the account root), then IAM identity policy when the key policy delegates, then grants; cross-account use needs both the key policy of the key and the identity policy in the caller's account.

**Conflict tracking** is a first-class output, in two forms:
1. **A decision trace per call** (format in [network-traces-plan.md](./network-traces-plan.md)): "denied: the key policy of `key-...` has no statement for `role/app` and does not delegate to IAM (no `arn:aws:iam::<acct>:root` principal), so the IAM allow in `policy/app-kms` is ignored".
2. **A conflict report per key and per account**, a static analysis of the stored policies and grants that does not need a call: 
   - IAM policies that allow KMS actions the key policy does not let them use (permission that looks granted and is not);
   - key policy allows that an SCP, a permission boundary or an explicit deny removes;
   - a key policy that would lock out administration (the check AWS performs on `PutKeyPolicy`, `MalformedPolicyException`, with its bypass flag);
   - principals in a key policy or grant that no longer exist (the `AROA...` ids AWS shows instead of an ARN);
   - cross-account use with only half of the permission (key policy allows the other account, nobody there is allowed by IAM, or the reverse);
   - key use by a service whose conditions the key policy does not satisfy (a `kms:ViaService` allow for the wrong service or Region, a missing `kms:GrantIsForAWSResource` for a service that needs a grant);
   - a key in a state that makes its dependents fail (disabled, pending deletion) with the list of resources that use it;
   - conflicting statements (an allow and a deny for the same principal and action, overlapping encryption context conditions).
   Each finding names the resources, the statements involved, and which call it breaks.

## Service encryption with AWS managed and AWS owned keys

Status: CloudFormation template storage with the AWS owned key is implemented (`src/app/api/kms/service-use.ts`, tests in `__tests__/cloudformation-kms.test.ts`); KMS per Region, aliases, AWS managed keys and the customer-key path of `kmsForService()` are planned. Every service that stores customer data encrypts it with a KMS key by default, without the customer choosing one. This section makes those calls happen in the simulator, so they are authorized, fail on a bad key state, and show up in CloudTrail. **Record-only**: the stored files stay plaintext and readable (the indented templates of CloudFormation stay as they are); only the KMS calls and the key ID next to the data are real.

### The two kinds of default key

| Kind | Who uses it | In the account? | Key policy | CloudTrail of the account |
|---|---|---|---|---|
| **AWS managed key** `alias/aws/<service>` | SSM `SecureString` (`aws/ssm`), Lambda environment variables (`aws/lambda`), S3 SSE-KMS without a key (`aws/s3`), Secrets Manager, EBS, ... | yes, created by the service on first use per account and Region; `KeyManager: AWS` | fixed by AWS: the account's principals may use it only through the service (`kms:ViaService = <service>.<region>.amazonaws.com`, `kms:CallerAccount = <account>`); read-only for everyone | `GenerateDataKey` / `Decrypt` with the caller as `userIdentity` and `invokedBy: <service>.amazonaws.com` |
| **AWS owned key** | CloudFormation templates, and the default of many services (DynamoDB, SQS SSE, ...) | no: not listed, not describable, no policy the customer can see or change | none for the customer; the service always may | nothing in AWS; the simulator records the calls as **simulated** events (`simulated: true`, like `iam:PassRole`) so they can still be traced |

CloudFormation has **no** `aws/cloudformation` managed key in AWS; its templates use an AWS-owned key. The simulator follows that.

### Building blocks

1. **KMS per Region and aliases** (prerequisite). Keys move from `data/accounts/<acct>/kms` to per-Region storage with the real Region in the ARN (today every key ARN says `us-east-1`). Aliases: `CreateAlias`, `DeleteAlias`, `ListAliases`, `UpdateAlias`, and `alias/...` / alias ARNs accepted wherever a `KeyId` is. `alias/aws/*` is reserved: customers cannot create, update or delete such aliases (`NotAuthorizedException`).
2. **AWS managed keys.** `managedKey(account, region, service)` returns the key behind `alias/aws/<service>`, creating it on first use with `KeyManager: AWS`, the AWS managed key policy, `Description: "Default key that protects my <Service> data when no other key is defined"`, and yearly rotation that cannot be turned off. `PutKeyPolicy`, `DisableKey`, `ScheduleKeyDeletion`, `DisableKeyRotation` on it fail as in AWS. Calling `Encrypt` on it directly (not through the service) is denied by its policy (`kms:ViaService`).
3. **AWS owned keys.** One simulator key per service and Region, kept outside every account (`data/aws/kms/<region>/<service>.json`, git-ignored), never listed or describable, no policy, never disabled. Real AES-GCM like any other key, so the record-only mode could later switch to real encryption without a format change.
4. **One path for services: `kmsForService()`** (new, `src/app/api/kms/service-use.ts`). `generateDataKey` / `decrypt` for a service acting for the caller of a request:
   - resolves the key (customer key ID/ARN/alias, `alias/aws/<service>`, or the AWS owned key);
   - authorizes the **caller**, not the service, with the key policy as the resource-based policy and the condition keys `kms:ViaService`, `kms:CallerAccount`, `kms:EncryptionContext:<k>` supplied, through the policy engine (which already evaluates supplied condition keys, see the `iam:PassRole` work); the key policy check replaces the separate evaluator in `kms/validator.ts` that S3 uses today;
   - checks the key state (`DisabledException`, `KMSInvalidStateException`, `NotFoundException`), turned into the calling service's error (S3: `KMS.DisabledException`);
   - records the CloudTrail event: `kms:GenerateDataKey` / `kms:Decrypt`, principal = the caller, `invokedBy` = the service, resource = the key ARN, the encryption context in the parameters; for AWS owned keys `simulated: true`, in the caller's account.
5. **Record-only storage.** Next to the data the service stores `{ kmsKeyId, encryptionContext }` (and later, in a real mode, the encrypted data key); the data itself stays as it is. The read path accepts data without this record (written before the change) and treats it as encrypted with the default key.

### CloudFormation template storage first

- **Write** (`CreateStack`, later `UpdateStack` and change sets): `kmsForService('cloudformation', 'GenerateDataKey', awsOwned)` with encryption context `{ "aws:cloudformation:stack-id": <stack id>, "templateVersion": "<n>" }`; then the template is written; `templates/v<n>.json` gets a sibling `v<n>.kms.json` with the key and context.
- **Read** (`GetTemplate`, `DescribeStacks` with the template, the deployment reading the template for the Python engine, later `GetTemplateSummary`): `Decrypt` with the stored context before the file is returned.
- **Expected trail of a CreateStack + GetTemplate:** `cloudformation:CreateStack` (caller) → `iam:PassRole` (simulated) → `kms:GenerateDataKey` (caller, `invokedBy: cloudformation.amazonaws.com`, simulated: AWS owned key) → ... → `cloudformation:GetTemplate` → `kms:Decrypt` (simulated).
- No customer key option: CloudFormation has none in AWS.

### Then

| Service | Data | Key | Calls |
|---|---|---|---|
| SSM | `SecureString` values (`Type: SecureString`, `KeyId` optional) | `KeyId` or `aws/ssm` | `PutParameter`: `Encrypt` (≤ 4 KB, Standard tier) or `GenerateDataKey` (Advanced); `GetParameter(s)` with `WithDecryption`: `Decrypt`; without it the value is returned as the ciphertext placeholder AWS returns |
| Lambda | environment variables (always), `KMSKeyArn` optional | `KMSKeyArn` or `aws/lambda` | `CreateFunction` / `UpdateFunctionConfiguration`: `GenerateDataKey` by the caller; every invocation: `Decrypt` by the **execution role** session (a disabled key then fails the invocation with `KMSDisabledException`) |
| S3 | objects with SSE-KMS (`aws:kms`), bucket default encryption | `SSEKMSKeyId` or `aws/s3`; SSE-S3 (`AES256`) uses an AWS owned key | `PutObject`: `GenerateDataKey`; `GetObject` / `HeadObject`: `Decrypt`; S3 Bucket Keys later (fewer KMS calls) |

Each one moves its KMS checks onto `kmsForService()`; S3 drops its own `checkKmsPermission`.

### Tests

- jest per building block: aliases and reserved `alias/aws/*`; managed key creation, policy and refused operations; owned key invisible to `ListKeys`/`DescribeKey`; `kmsForService` allow/deny (wrong account, missing `kms:ViaService`, explicit deny in an IAM policy, disabled customer key), and the CloudTrail event shape.
- End-to-end with the AWS CLI per service: the CloudFormation case is the trail above; then SSM `put-parameter --type SecureString` + `get-parameter --with-decryption`, a Lambda with environment variables invoked after its key is disabled, S3 `put-object --server-side-encryption aws:kms`.

## ACM and certificates

**Interpretation to confirm:** the emulated ACM issues *real X.509 certificates* so that TLS is genuinely terminated by the simulator, and real certificates can be imported. Both halves:
- **A simulator CA** (a root and an intermediate, generated once and stored under `db/`, with the certificate exported for trust stores and CA bundles). `RequestCertificate` produces a real certificate for the requested domain names and subject alternative names, signed by it, with the real validity period, key algorithm and serial; `GetCertificate` returns the PEM chain, `DescribeCertificate` the details ACM shows (status, `DomainValidationOptions`, `InUseBy`, `NotBefore`/`NotAfter`, `RenewalEligibility`, `Type`).
- **Validation is simulated**: a `DNS` validation request creates the CNAME records to be added; when the record exists in the emulated Route 53 zone (the [Route 53 plan](./network-connectivity-plan.md)) the certificate moves from `PENDING_VALIDATION` to `ISSUED`; `EMAIL` validation is approved by an admin call. There is no real domain ownership check; the simulator never contacts real DNS or a real CA.
- **`ImportCertificate`** accepts real certificates (parsed, chain and key checked, expiry known), so a certificate from a real CA can sit in the simulation; private keys are stored only in the simulator's `db/` and never in a snapshot.
- **Lifetime**: a certificate in use by a load balancer, CloudFront distribution or API Gateway domain cannot be deleted (`ResourceInUseException`, with `InUseBy`); expiry and renewal are modelled (`ISSUED`, `EXPIRED`, `PENDING_VALIDATION`, `FAILED`, `VALIDATION_TIMED_OUT`, `REVOKED`); quotas (certificates per account, domain names per certificate) through the registry.
- **TLS in the network model**: an emulated endpoint (an ALB listener, an API Gateway custom domain, an S3 virtual-hosted name) presents the certificate attached to it, and a client that trusts the simulator CA completes the handshake; a name that is not on the certificate, an expired certificate or an untrusted CA fails like it would. This is also the way out of the "no TLS" limitation of the in-process shim ([walking-skeleton.md](./walking-skeleton.md)): the shim passes the CA bundle (`AWS_CA_BUNDLE`, `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`) to the run and the server terminates TLS for the AWS service names with certificates the simulator CA issues for them.
- ACM Private CA (`acm-pca`) is the same machinery with a customer-owned CA; later.

## Order

1. KMS records and the control-plane API (keys, aliases, policies, states, grants) with access evaluation limited to key policy plus the IAM delegation rule, and the trace output.
2. Manual encryption: symmetric `Encrypt` / `Decrypt` / `GenerateDataKey` / `ReEncrypt`, then asymmetric and HMAC.
3. Service integrations as fake encryption ("Service encryption with AWS managed and AWS owned keys"): KMS per Region and aliases, AWS managed and AWS owned keys, `kmsForService()`, then CloudFormation template storage first, then SSM, Lambda, S3, Secrets Manager.
4. The conflict report, once the policy engine can evaluate IAM policies, SCPs and boundaries.
5. ACM with the simulator CA, then import, then validation through Route 53, then TLS termination in emulated endpoints.
6. Optional real at-rest encryption for S3.

## Open questions

- "Real certificates from ACM": the plan assumes real X.509 issued by a simulator CA plus import of real ones. If the intention was something else (for example pulling real certificates from a real account in the snapshot plan, which is possible for public certificates but never for private keys), say so.
- Should KMS ciphertexts be made compatible with real AWS KMS? Not possible without the real service's keys; keep them simulator-only and document it.
- How strict is the "manual encryption" requirement for key import and for asymmetric key specs beyond RSA and P-256 / P-384?
